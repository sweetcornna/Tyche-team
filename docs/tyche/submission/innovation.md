# 创新点说明

## 1. 证据约束的论文生成：模型提议，代码核验

通用写作智能体的主要风险是编造参考文献和结果数字。Tyche 在结构上排除这两类错误：

- **文献只来自核验过的检索结果**。参考文献只取自 arXiv、Semantic Scholar、OpenAlex 的真实响应，要求具备标题、作者、年份与持久标识，并回查 arXiv 或 Crossref 确认一致后才写入 `refs.bib`。证据卡中的每条观点都必须附一段摘要原文，代码逐字比对，不符即丢弃。评审要求补充讨论某篇论文时，该论文先经同一个核验器，通过后才进入允许引用列表。
- **数字只来自统计代码**。确定性代码从实验指标文件计算均值、bootstrap 置信区间与配对置换检验，生成“允许数字登记表”。数字门禁逐个检查摘要、引言、实验、分析与结论中的数字，任何数字都必须是登记值按其精度的四舍五入或其百分比形式，否则无法打包。
- **AI 使用声明由代码生成**。ICLR 2027 要求的 AI use statement 与复现声明根据运行记录生成，披露的模型、用途与核验方式和实际运行一致。

## 2. 可离线复核的交付：`tyche verify`

每篇论文的打包目录自带全部产物版本、SHA-256 溯源、实验指标与生成代码、事件与用量日志。`tyche verify` 只用打包目录就能完成全部核验，不需要网络，也不调用模型：

1. 重算全部哈希；
2. 由指标文件重算统计量与允许数字登记表，并逐字节比对；
3. 检查正文中的每个数字；
4. 确认每个引用都来自已核验记录；
5. 重建论断–证据地图并比对。

复现审核方可以在几秒内确认论文中的每个数字和引用都有来源，而无需重跑耗时数小时的模型流程。

## 3. 严谨的逐条目统计

实验代码常用子集或剔除规则报告指标，例如只统计评估阶段，或排除调用失败的条目。Tyche 从逐条目结果中搜索能**同时复现所有变体报告值**的同一条子集规则，再在这一子集上做配对比较。如果多条规则都能复现，但选出的条目集合不同，n、置信区间与配对检验一律不报告，并注明原因。每个区间与 p 值使用由（种子、指标、变体）派生的独立随机数流，增减其他指标不会改变已有数字。天花板与地板效应、完全相同的逐条目结果（平局）都会被自动标注，写作阶段必须如实表述。

## 4. 面向 Agentic Reviewer 的评审修订闭环

- 三位视角评审（严谨性、定位、清晰度）按 Stanford Agentic Reviewer 公开的 7 个维度打分，另有一位忠实度审计员对照结果简报与证据卡检查误引、夸大与遗漏的局限。
- 每条发现都必须附论文原文的逐字引文，代码核对引文确实存在，以此抑制评审的幻觉式批评。发现进入带生命周期的台账（open → resolved / wontfix / unaddressed），写作者需逐条回复，下一轮评审逐条裁决。
- 修订只作用于有待处理发现的章节。候选稿只有同时满足以下条件才被接受，否则回滚：编译通过，阻断项不增加，不出现新的重大门禁问题，综合分下降不超过容差。评审只能要求改写，不能要求补做实验；证据不足时应收窄结论。

## 5. 像编码智能体一样写论文

Tyche 的规划、写作与评审借鉴 Claude Code 与 Codex 的工作方式：模型通过工具循环完成任务，写论文和写代码一样，改完先检查。这里只借鉴理念，没有复制它们的代码与提示词。

- **改完就查**：作者智能体每次写入或编辑章节，宿主都会先做确定性清洗，再立即检查该节的数字、引用、结构与术语，结果随工具结果返回，相当于编辑后的诊断反馈。
- **检查不过不能结束**：作者要结束时，宿主编译全文并运行全部门禁，有问题就把问题退回，最多退回若干次。编译失败、数字无出处、缺少局限性段落这类问题在写作阶段就被发现并修正，不用等到评审阶段。
- **精确编辑**：修订用唯一匹配的原文替换，只改评审指出的地方，不重写整节，也就不会顺手改坏正确的数字和引用。
- **评审先核对再下结论**：每位评审都是独立的只读会话，可以查允许数字、检索被引论文的证据，核对之后才提交报告，减少凭印象的批评。
- **子智能体与压缩**：作者可以把事实核查委派给在全新上下文中工作的助手；对话接近上下文上限时先写工作摘要，再继续，而不是截断。
- **可审计**：权限模式限定每类智能体能用的工具，待办清单与工具调用实时显示在工作台，每个会话的完整转录进入运行记录。

证据边界没有变：没有任何工具能登记数字、加入参考文献或让门禁通过，智能体越主动，门禁越早发挥作用。

## 6. 复用 openJiuwen 实验闭环，并补齐其短板

Tyche 直接驱动 openJiuwen `auto_research` 的 `ManagerRuntime` 完成实验设计、编码、真实执行与反思，没有另写一套实验框架。在此基础上，Tyche 用子类与公开参数补齐了几处问题：

- 编码智能体的轮次上限过低；
- 设计修订后编码可能空转；
- 沙箱内读不到输入文件；
- 被中断的尝试需要续跑，旧变体不能混入结果。

Tyche 还把调用预算、逐条目记录、缓存友好的提示结构等要求作为硬约束交给实验智能体。

## 7. 与赛题三个方向的双重对应

Tyche 能就三个方向生成论文（`--direction context_engineering | memory_engine | self_evolution`，每个方向带种子查询、经典工作与可执行的实验族），而它自身也实现了这三项技术：

- **记忆引擎**（`tyche/memory/store.py`）：带来源类型、作用域、更正链与使用记录的科研记忆，基于 SQLite FTS5 与 BM25 检索。重跑某一阶段时，旧条目会被标记失效，不再进入提示词。
- **上下文工程**（`tyche/memory/context_pack.py`）：每次调用由必选块与按优先级纳入的可选块组成，在硬 token 预算内装配，超长块截断而不是静默丢弃。装配清单逐次落盘，可以审计；稳定的共享前缀使服务端提示缓存命中率很高（见 `resource_report.md`）。
- **自演进**（`tyche/evolution/playbook.py`）：评审发现 → 经验候选 → 在多次运行中复现，且相关修复被接受、分数未降，才晋升为生效经验 → 失效后自动淘汰。导出格式为 JiuwenSwarm 技能的 `evolutions.json`，与 JiuwenSwarm 的技能演进机制互通。

## 8. 可观察、可干预的科研工作台

`tyche ui` 提供桌面聊天应用式的本机工作台，支持以下操作：

- 发起运行，审批研究计划（附修改意见）；
- 实时查看 openJiuwen 实验事件，以及 Tyche 智能体的待办清单、工具调用、编译结果与检查退回；
- 逐轮查看评审修订的差异；
- 按句查看论断–证据地图，追溯产物谱系与环境快照。

界面内容全部来自确定性代码与已有产物，不会让模型改写任何证据。工作台默认只监听本机，并做 Host/Origin 校验与访问令牌保护。
